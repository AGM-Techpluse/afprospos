# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AfProsPos — a phone sales, repair & business management system. Laravel 13 (PHP 8.3+) modular monolith, DDD/hexagonal architecture, CQRS-lite, Inertia.js + React 19 (TypeScript) frontend, Tailwind CSS 4, MySQL 8/InnoDB.

Laravel Boost is installed; `AGENTS.md` (generated by `php artisan boost:install`) carries the full Boost/Laravel/Pint/PHPUnit/Inertia rule set — read it too, it is not duplicated here.

## The binding architecture contract

**`documentation/AfProsPos_Codebase_Principles_and_Naming_Conventions.md` (CPNC) is a binding conformance spec, not a style guide.** Read it before writing or refactoring any domain/application/infrastructure code — it governs naming, layering, and file placement in more detail than is restated below, and code review is expected to reject anything that deviates without a written exception. Companion documents, same authority tier:

- `documentation/AfProsPos_Architecture_Design_Document.md` (ADD) — canonical directory trees (backend §5, frontend §5A), page-level layout specs (§14C).
- `documentation/AfProsPos_Database_Design_Document.md` (DBDD) — schema, money/ledger rules, delete policy.
- `documentation/AfProsPos_UI_UX_Design_System_Document.md` — token architecture, component contracts.
- `documentation/AfProsPos_Implementation_Plan.md` — phase plan and per-phase file lists; check this before starting new module work to see which phase it belongs to and what "done" looks like.

The five things to never violate (CPNC §0, condensed):

1. **Reuse before you invent** — grep `domain/` for an existing Contract/DTO/Value Object/Component before creating one.
2. **`domain/<Module>/Domain/` touches nothing external** — no Eloquent, no `Illuminate\Http`, no vendor SDK, no queue facade, no other module's Eloquent/domain class.
3. **One write path only:** `Route → Controller → Command DTO → Handler → Domain Aggregate → Repository/Gateway`. Controllers never call Eloquent or contain business conditionals.
4. **Names describe business reality**: events are past-tense facts (`RepairCompleted`, not `UpdateRepairStatus`); contracts have no `Interface`/`Impl` suffix (`PaymentGateway`, `PaystackGateway`); Eloquent models are suffixed `Record` and live only under `Infrastructure/Persistence/Eloquent/`, never `app/Models/`.
5. **Laravel owns navigation, React owns interaction** — `routes/*.php` is the only router; `react-router-dom` must never be added.


`tests/Architecture` enforces CPNC §4.5's boundary rules (domain-layer dependency direction, Command/Handler pairing, Contract implementation coverage, audit-log append-only) via a small `nikic/php-parser`-based static scanner (`tests/Architecture/Support/DependencyScanner.php`) rather than Pest-arch — the project uses plain PHPUnit, not Pest. Extend that scanner/tests rather than adding a second architecture-testing tool.

There is no PHPStan/Larastan config in the repo yet, despite CPNC/Implementation Plan calling for it in CI — don't assume static analysis is wired up.

## Architecture

### Backend: `domain/` is the real application, `app/` is the Laravel shell

Business code lives in `domain/<Module>/`, one folder per bounded context (`Identity`, `RBAC`, `Shop`, `Shared`, `Audit`, `Inventory`, `Sales`, `Payments`, `Repair`, `Commission`, `Warranty`, `Marketing`, `Referral`, `Collection`, `Finance`, `Notifications`, `Sync`). Every module has exactly this shape (see CPNC Appendix C for the full skeleton):

```
domain/<Module>/
├── Domain/          Entities, ValueObjects, Services, Policies, Events, Exceptions, Repositories (pure PHP, no framework)
├── Application/     Commands, Queries, DTOs, Handlers, Contracts (orchestration; still framework-light)
└── Infrastructure/  Persistence/Eloquent (*Record models), Persistence/Repositories (Eloquent[Entity]Repository), Laravel (ServiceProvider)
```

`app/` only holds framework glue: `Http/Controllers/{Admin,Customer,Auth}`, `Http/Middleware`, `Http/Requests`, `Providers`, `Models` (should stay near-empty — domain Eloquent models belong under `domain/*/Infrastructure/Persistence/Eloquent/`, not here).

Currently implemented with real code: `Identity`, `RBAC`, `Shop`, `Shared`, `Audit` — Phase 1 (auth, shop scoping, RBAC, staff/shop/role admin CRUD) plus Phase 2 (shared UI shells); `Inventory` — Phase 3 (product/SKU catalog, serialized IMEI + non-serialized stock, the On-hand/Reserved/Available reservation engine, transfers, low-stock detection, invariant reconciliation); and `Sales` — Phase 4 (POS checkout/cart, the checkout reservation model built on Inventory's contract, discount/adjustment stacking, cash/POS-terminal/bank-transfer sale completion, invoice/receipt generation, checkout expiry). RBAC roles are real, admin-editable database rows (Spatie `Role`/`Permission`, guard `staff`) — not a fixed config catalog; only the *set of assignable permissions* (`config('afprospos.permissions')`) is code-defined. Every other module directory (`Payments`, `Repair`, `Commission`, `Warranty`, `Marketing`, `Referral`, `Collection`, `Finance`, `Notifications`, `Sync`) exists only as an empty skeleton for a future phase — don't assume they have any implementation to build on.

Inventory's reservation engine (`domain/Inventory/Application/Handlers/{Reserve,Consume,Release}InventoryHandler.php`) is the concurrency-safety boundary Sales (Phase 4) and Repair (Phase 6) depend/will depend on via `Domain\Inventory\Application\Contracts\InventoryReservationService` — call that contract, never the Handlers directly, from another module. Available stock (`on_hand - reserved`) is computed on the fly by `Domain\Inventory\Domain\Services\StockAvailability` and is never persisted as its own column. Inventory also publishes a read-side `Domain\Inventory\Application\Contracts\InventoryCatalogQuery` contract (search/find by SKU+shop) for exactly this kind of cross-module read — Sales' checkout Handlers depend on it rather than reaching into Inventory's own Query classes directly.

Sales' checkout (`domain/Sales/Domain/Entities/SalesCheckout.php`) mutates only while `status = 'open'`; once `paid`/`expired`/`cancelled` it's terminal (DBDD §40: "paid checkout cannot expire; expired checkout cannot become paid"). A checkout's inventory reservation is scoped by `sourceType: 'checkout'` (the shared string Inventory's schema fixes for both Sales and Repair — not `'sales_checkout'`, that value doesn't exist in `inventory_items.reserved_by_type`'s enum). Discount/adjustment stacking is non-stackable by default this phase (applying a new adjustment replaces any existing one) — see `Domain\Sales\Domain\Services\CheckoutPricingService` for the exact MKT-BR-07 ordering.

Cross-module calls go through `Application/Contracts/` interfaces and pass IDs, never another module's Eloquent model or a database foreign key (the only exception is the Shared Kernel: `shops.id`, `customers.id`, `staff.id`).

### Routing

Route files are audience-scoped, not resource-scoped: `routes/admin.php`, `routes/customer.php`, `routes/api.php`, `routes/webhooks.php`, `routes/web.php`, `routes/console.php`. A Controller action maps to exactly one Command or one Query — never both in the same method.

### Frontend: three-tier component model (CPNC §5.2)

```
resources/js/Pages/       Inertia entry points, 1:1 with a controller action. No reusable UI logic.
resources/js/Components/  Dumb, reusable, presentation-only primitives (Admin/, Customer/, Feedback/, Forms/, Tables/, Icons/). No domain knowledge.
resources/js/Features/    Domain-specific interactive components (not yet created — arrives with Phase 3+ modules).
```

`Components/Admin/` and `Components/Customer/` keep field components (`AdminInput`, `AdminSelect`, `AdminTextarea`, `CustomerInput`) in a `Forms/` subfolder; `AdminButton`/`CustomerButton` stay flat at the theme root (buttons and forms are separate UI/UX sections). Don't create a one-file subfolder for anything else.

All colors/spacing/radii flow through Tailwind theme utilities backed by CSS variables in `resources/css/tokens.css` (`bg-admin-surface`, `text-customer-blue`, etc.) — raw hex values and arbitrary Tailwind color values are forbidden outside `tokens.css`/`tailwind.config.js` itself. Icons come from Bootstrap Icons via `resources/js/Components/Icons/Icon.tsx`; no emoji as UI iconography.

React state may mirror server state for responsiveness but is never authoritative — a Feature must never render a final success state (e.g. "Payment Successful") without a server round-trip confirming it.

**Forms are never wrapped in a decorative card** (UI/UX §10.1's Core Rule, "Invariant #19") — a `<form>` sits directly on the page (`admin-bg`/page background), never inside a bordered/shadowed `admin-surface` panel, on Admin or Customer. This has been violated and re-fixed multiple times across revisions (see the doc's own changelog) — don't reintroduce it. Bordered/surfaced containers are still fine for *data display* (tables, stat cards, a Staff/Shop detail view) — the rule is specifically about the form itself.

### Testing tiers (CPNC §6)

| Tier | Location | Naming | DB/framework |
|---|---|---|---|
| Unit | `tests/Unit/Domain/<Module>/` | `[Subject][Behavior]Test` | none — pure PHP |
| Integration | `tests/Integration/<Module>/` | `[Command]IntegrationTest` | Command → Handler → Repository → DB, no HTTP |
| Feature | `tests/Feature/{Admin,Customer}/<Module>/` | `[PersonaCan/CannotAction]Test` | full boot + DB |
| Concurrency | `tests/Feature/<Module>/Concurrency/` | `[Scenario]ConcurrencyTest` | real MySQL, genuinely parallel OS processes |
| Architecture | `tests/Architecture/` | `[Boundary]ArchTest` | static, no DB |

A "Cannot" feature test must assert both the HTTP rejection and that no state mutation occurred, not just the status code.

Concurrency tests need a real, persistent MySQL database shared across OS processes — SQLite `:memory:` can't do that, so they're excluded from the default run (`phpunit.xml`'s `Feature` testsuite explicitly excludes `tests/Feature/Inventory/Concurrency`) and must be run explicitly: `php artisan test --testsuite=Concurrency`. They spin up a dedicated `afprospos_concurrency_test` MySQL database (never the dev `afprospos` one) and spawn real child PHP processes via `Symfony\Process` — see `tests/Feature/Inventory/Concurrency/Support/`.

### Config

`config/afprospos.php` centralizes business constants referenced by name across modules: the owner role name (`Shop Owner`, the one role that bypasses shop-scope restriction), the RBAC permission catalog, and starting role→permission grants seeded by `database/seeders/DatabaseSeeder.php`. Modules not yet built still have permissions seeded here ahead of time so later phases consume an already-agreed catalog.

## Git workflow

`documentation/AfProsPos_Git_Branching_Strategy.md` is binding, same tier as CPNC. Short version: trunk-based with phase integration branches pre-launch — `phase/<n>-<slug>` off `main`, `feature/<n>-<slug>` off the active phase branch, `fix/<slug>`/`chore/<slug>` off `main` for anything unrelated to the in-flight phase. No direct pushes to `main` or any `phase/*` branch. `feature/* → phase/*` squash merges; `phase/* → main` is always a merge commit, never squashed, so `git log --graph main` shows each phase as a milestone. Tag `main` at the end of every phase (`v0.<n>.0-phase<n>`). Commit messages follow Conventional Commits (`type(scope): summary`, scope = lowercased module name) and PR descriptions should cite the BRD/BLD rule IDs implemented. Read the doc itself before starting a new phase's branch — this is a summary, not the full rule set (hotfix lane, branch protection settings, etc.).
